# Deploy to VPS with Docker Compose

This guide walks you through deploying the SaaS Boilerplate to a VPS using Docker Compose with Traefik for automatic SSL.

## Prerequisites

- A VPS (Hetzner, DigitalOcean, Linode, Vultr, etc.)
  - Minimum: 2 vCPU, 4GB RAM, 40GB SSD
  - Recommended: 4 vCPU, 8GB RAM, 80GB SSD
- A domain name pointed to your VPS IP
- SSH access to your VPS

## VPS Provider Recommendations

| Provider | Recommended Plan | Monthly Cost |
|----------|-----------------|--------------|
| Hetzner | CX21 (2 vCPU, 4GB) | ~€5/month |
| DigitalOcean | Basic Droplet 4GB | ~$24/month |
| Linode | Linode 4GB | ~$24/month |
| Vultr | Cloud Compute 4GB | ~$24/month |

## Quick Start with CLI

Deploy from your local machine using the SaaS Boilerplate CLI:

```bash
# One-time setup - configures SSH connection and generates docker-compose
saas vps setup

# Deploy to VPS (uploads files, pulls images, starts services)
saas vps deploy

# Run migrations after first deploy
saas vps deploy --migrate

# Check service status
saas vps status

# SSH into VPS for manual commands
saas vps ssh
```

The setup wizard will guide you through:
1. Configuring SSH connection (host, user, key path)
2. Generating `docker-compose.prod.yml` with your domain
3. Creating secure credentials

## Manual Deployment

If you prefer manual control, follow these steps:

<Steps>
<Step title="Initial Server Setup">

SSH into your VPS and install Docker:

```bash
# Update system
sudo apt update && sudo apt upgrade -y

# Install Docker
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER

# Install Docker Compose plugin
sudo apt install docker-compose-plugin -y

# Install useful tools
sudo apt install git htop -y

# Log out and back in for docker group
exit
```

</Step>

<Step title="Configure DNS">

Point your domain to your VPS IP:

| Type | Name | Value |
|------|------|-------|
| A | @ | YOUR_VPS_IP |
| A | api | YOUR_VPS_IP |

Wait for DNS propagation (5-15 minutes).

</Step>

<Step title="Clone Repository">

```bash
# Create app directory
sudo mkdir -p /opt/saas-app
sudo chown $USER:$USER /opt/saas-app
cd /opt/saas-app

# Clone repository
git clone https://github.com/your-org/your-fork.git .
```

</Step>

<Step title="Configure Environment">

Copy the example environment file and customize:

```bash
cp .env.vps.example .env.prod
```

Edit `.env.prod` with your values:

```bash
nano .env.prod
```

:::tip Quick Reference
See `.env.vps.example` in the project root for all available options with detailed comments.
:::

**Required variables:**

```bash
# Domain configuration
DOMAIN=example.com
ACME_EMAIL=admin@example.com

# Security secrets (generate unique values!)
DJANGO_SECRET_KEY=<generate-me>
HASHID_FIELD_SALT=<generate-me>
POSTGRES_PASSWORD=<generate-me>

# Email configuration
EMAIL_BACKEND=sendgrid_backend.SendgridBackend
SENDGRID_API_KEY=SG.your-api-key
EMAIL_FROM_ADDRESS=noreply@example.com
```

**Generate secure secrets:**

```bash
# Django secret key
python3 -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"

# Hashid salt and Postgres password
openssl rand -hex 32
```

For complete environment variable reference, see [Environment Variables](/deployment/environment-variables).

</Step>

<Step title="Deploy">

```bash
# Start all services
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d

# Check status
docker compose -f docker-compose.prod.yml ps

# View logs
docker compose -f docker-compose.prod.yml logs -f
```

</Step>

<Step title="Run Migrations">

```bash
docker compose -f docker-compose.prod.yml exec backend python manage.py migrate
```

</Step>

<Step title="Create Superuser">

```bash
docker compose -f docker-compose.prod.yml exec backend python manage.py createsuperuser
```

This account is created with its email unconfirmed (`is_confirmed=False`) - expected, not
a bug: nothing checks that flag for Django admin login or the global `Admin`/`Support`
group permissions, it only gates tenant-facing "confirm your email" flows. It flips to
confirmed automatically the first time this account logs into the webapp via Google/
Facebook (or leave it as-is if you only ever use it for `/admin/`).

</Step>
</Steps>

## Storage Options

### Local Filesystem (Default)

Files are stored in a Docker volume. Good for small deployments.

```bash
STORAGE_BACKEND=local
```

### Cloudflare R2

For production, use R2 for durability and CDN integration:

```bash
STORAGE_BACKEND=r2
R2_ENDPOINT_URL=https://account-id.r2.cloudflarestorage.com
R2_ACCESS_KEY_ID=your-key
R2_SECRET_ACCESS_KEY=your-secret
R2_BUCKET_NAME=your-bucket
```

### MinIO (Self-Hosted S3)

Add MinIO to your docker-compose.prod.yml:

```yaml
services:
  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
    volumes:
      - minio_data:/data
    environment:
      - MINIO_ROOT_USER=minioadmin
      - MINIO_ROOT_PASSWORD=minioadmin
    networks:
      - internal

volumes:
  minio_data:
```

### AWS S3

For off-VPS durability (uploaded documents surviving a VPS rebuild, not just living in a
Docker volume):

```bash
STORAGE_BACKEND=s3
AWS_ACCESS_KEY_ID=your-key
AWS_SECRET_ACCESS_KEY=your-secret
AWS_DEFAULT_REGION=eu-central-1
AWS_STORAGE_BUCKET_NAME=your-bucket
```

`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_DEFAULT_REGION` are picked up
automatically by boto3 - only `AWS_STORAGE_BUCKET_NAME` is explicitly read by Django
settings. Use an IAM user scoped to just this bucket (`s3:GetObject`/`PutObject`/
`DeleteObject`/`ListBucket`), not admin credentials.

## Email

`EMAIL_BACKEND` selects the provider - generic SMTP, SendGrid, or AWS SES (see
`.env.vps.example` for all three). SES setup has the most one-time steps, documented
here since nothing in the boilerplate automates domain verification:

### AWS SES

1. **Create the domain identity** (generates DKIM tokens):
   ```bash
   aws sesv2 create-email-identity --email-identity yourdomain.com --region eu-central-1
   ```
   The response includes 3 `DkimAttributes.Tokens` - add each as a CNAME in your DNS:
   `<token>._domainkey.yourdomain.com` -> `<token>.dkim.amazonses.com`.

2. **Set a custom MAIL FROM domain** (recommended - improves deliverability/DMARC
   alignment):
   ```bash
   aws sesv2 put-email-identity-mail-from-attributes \
     --email-identity yourdomain.com \
     --mail-from-domain mail.yourdomain.com \
     --behavior-on-mx-failure USE_DEFAULT_VALUE \
     --region eu-central-1
   ```
   Add an MX record (`mail.yourdomain.com` -> `feedback-smtp.eu-central-1.amazonses.com`,
   priority `10`) and a TXT record (`mail.yourdomain.com` -> `v=spf1 include:amazonses.com
   ~all`).

   If your DNS is behind Cloudflare (or another proxying provider), set these records to
   **DNS only** - a proxied CNAME breaks SES's ability to see the real verification
   target.

3. **Check verification status**:
   ```bash
   aws sesv2 get-email-identity --email-identity yourdomain.com --region eu-central-1
   ```
   Look for `"VerificationStatus": "SUCCESS"` and `"DkimAttributes.Status": "SUCCESS"`.
   With Cloudflare this is often done within minutes; other providers may take longer.

4. **Request production access** - new accounts start in a sandbox (200 emails/24h,
   1/sec, verified recipient addresses only):
   ```bash
   aws sesv2 put-account-details \
     --mail-type TRANSACTIONAL \
     --website-url https://yourdomain.com \
     --contact-language EN \
     --use-case-description "Describe what you send and to whom." \
     --production-access-enabled \
     --region eu-central-1
   ```
   Check status with `aws sesv2 get-account --region eu-central-1` (`ReviewDetails.Status`
   goes `PENDING` -> `GRANTED`, usually within a few hours).

   A first request can come back `DENIED` (seen on this project) if the use-case
   description is too generic - AWS wants specifics: what the app is, what kind of email
   it sends (transactional vs. marketing), roughly how many/how often, and how recipients
   end up subscribed (e.g. "transactional account/security emails - signup confirmation,
   password reset, notifications - triggered by user actions on our app, a B2B SaaS
   product; no marketing sends"). You can resubmit `put-account-details` with a more detailed
   description; there's no cooldown penalty for a prompt, well-explained resubmission.
   Until granted, the account stays sandboxed - verify individual recipient addresses with
   `aws sesv2 create-email-identity --email-identity <address> --region eu-central-1` (a
   confirmation link is emailed to that address) so you can test end-to-end in the
   meantime.

5. **Grant the sending IAM user permission**, scoped to just this identity:
   ```json
   {
     "Effect": "Allow",
     "Action": ["ses:SendEmail", "ses:SendRawEmail"],
     "Resource": "arn:aws:ses:eu-central-1:<account-id>:identity/yourdomain.com"
   }
   ```

6. **Set in `.env`**:
   ```bash
   EMAIL_BACKEND=django_ses.SESBackend
   AWS_SES_REGION_NAME=eu-central-1
   EMAIL_FROM_ADDRESS=noreply@yourdomain.com
   # AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY/AWS_DEFAULT_REGION as usual (see Storage Options)
   ```

## OAuth / Social Login

Google/Facebook login needs an OAuth client created in each provider's developer console
before the buttons work - nothing in the boilerplate automates this (same category of
one-time external setup as the SES steps above).

### Google

1. **Create the OAuth client under the organization's own Google account, never a
   developer's personal Gmail.** A personal-account-owned client puts a business-critical
   login path - and the only way to rotate/revoke its secret or see who's used it - under
   one person's personal account, with no team access if they leave and none of Google
   Workspace's org-level controls (admin recovery, audit logs, app verification as the
   org). Sign in with an org Google Workspace account at
   [Google Cloud Console](https://console.cloud.google.com/) -> APIs & Services ->
   Credentials, in a project owned by the organization (not a personal project).
2. Configure the OAuth consent screen - app name/logo, and a support email that's an org
   mailbox, not a personal address - requesting only the default `email`/`profile` scopes
   (no sensitive-scope verification needed for those).
3. Create an **OAuth 2.0 Client ID** (Web application type) with:
   - Authorized redirect URI: `https://api.DOMAIN/auth/social/complete/google-oauth2/`
4. Set in `.env.prod`:
   ```bash
   SOCIAL_AUTH_GOOGLE_OAUTH2_KEY=<client id>
   SOCIAL_AUTH_GOOGLE_OAUTH2_SECRET=<client secret>
   ```
   `SOCIAL_AUTH_ALLOWED_REDIRECT_HOSTS` does **not** need to be set separately - unlike the
   two vars above, `docker-compose.prod.yml` already derives it from `DOMAIN`
   (`SOCIAL_AUTH_ALLOWED_REDIRECT_HOSTS=${DOMAIN}`), which is what lets the post-login
   redirect land back on the webapp host (`DOMAIN`) instead of the API host
   (`api.DOMAIN`) the OAuth flow itself runs on.
5. If the consent screen is left in "Testing" mode, only explicitly-added test users can
   log in - publish it to Production once ready (no Google app verification step is
   required for the default, non-sensitive scopes used here).

### Facebook

Same shape, via [Meta for Developers](https://developers.facebook.com/) - create the app
under the organization's Business Manager, not a developer's personal Facebook account,
for the same ownership reason as Google above. Redirect URI:
`https://api.DOMAIN/auth/social/complete/facebook/`.

## AI Assistant (MCP Server) - Optional

The MCP Server enables AI assistants to interact with your application's data. It's included in `docker-compose.prod.yml` and will start automatically with your other services.

### Configuration

The MCP server is pre-configured to connect to your backend. Add these variables to `.env.prod` if you want to enable AI features:

```bash
# AI Assistant Configuration
OPENAI_API_KEY=sk-your-openai-api-key

# MCP Server is accessible internally at http://mcp-server:4000
# The backend uses this URL to proxy AI requests
```

### Verifying MCP Server

After deployment, check that the MCP server is running:

```bash
# Check container status
docker compose -f docker-compose.prod.yml ps mcp-server

# View logs
docker compose -f docker-compose.prod.yml logs mcp-server
```

### Disabling MCP Server

If you don't need AI features, you can exclude the MCP server from deployment:

```bash
# Start all services except mcp-server
docker compose -f docker-compose.prod.yml up -d --scale mcp-server=0
```

Or remove the `mcp-server` service from your `docker-compose.prod.yml`.

## Backups

Three independent backup mechanisms. The first two need a cloud storage backend
configured (see [Storage Options](#storage-options) above) - `local` storage means
backups only live in a VPS Docker volume, with no offsite copy if the VPS itself dies.

### Full Database Backups (Postgres -> S3)

`scripts/backup-postgres-to-s3.sh` (checked into the repo, kept in sync on the VPS by
`deploy-vps.yml`) dumps the database via the running `db` container and uploads it to
S3 using a one-off `amazon/aws-cli` container - no extra long-running service needed.

Add to `.env` on the VPS:

```bash
BACKUP_S3_BUCKET=your-backups-bucket
AWS_ACCESS_KEY_ID=your-key
AWS_SECRET_ACCESS_KEY=your-secret
AWS_DEFAULT_REGION=eu-central-1
```

Then add to crontab:

```bash
# Run daily at 3 AM
0 3 * * * cd /opt/klarvido && ./scripts/backup-postgres-to-s3.sh >> /var/log/klarvido-backup.log 2>&1
```

Retention is handled by an S3 Lifecycle rule on the bucket (e.g. expire after 30 days),
not by the script - set it once when creating the bucket.

### Per-Tenant Data Backups (built-in)

The app also has a built-in, per-tenant encrypted backup/restore feature (`apps.backup`
+ `webapp-backup`) that XML-exports a tenant's data on a configurable schedule via
Celery Beat (runs hourly, checking each tenant's config) and emails recipients when
ready. Tenant owners/admins enable and configure it from within the app; it needs:

```bash
# Fernet key encrypting per-tenant backup keys (DB fallback - no AWS Secrets Manager on a VPS)
# Generate with: openssl rand 32 | base64 | tr '+/' '-_'
BACKUP_MASTER_KEY=your-generated-key
```

Exported files are written through the configured `STORAGE_BACKEND`, so they land in
the same S3 bucket as other uploads (under an `exports/` prefix) once S3 storage is set
up above - not a separate bucket.

### Backing Up `.env` Itself

`.env` on the VPS holds `DJANGO_SECRET_KEY`, `POSTGRES_PASSWORD`, AWS credentials,
`BACKUP_MASTER_KEY`, Stripe/OAuth secrets, etc. It's never committed and lives only on
the VPS disk - if the VPS is lost, this file is lost with it, which also makes the two
backups above unusable (no `BACKUP_MASTER_KEY` to decrypt per-tenant exports, no AWS
credentials to even reach the buckets). `scripts/backup-env-to-s3.sh` encrypts `.env`
with a passphrase and uploads it to the same backups bucket.

One-time setup on the VPS:

```bash
openssl rand -base64 48 > /opt/klarvido/.env-backup-key
chmod 600 /opt/klarvido/.env-backup-key
```

**Copy that passphrase into a password manager immediately** - it's the only offsite
copy. The key file on the VPS is only there so the cron job can encrypt automatically;
it does you no good if the VPS is what died.

Then add to crontab (right after the Postgres dump):

```bash
15 3 * * * cd /opt/klarvido && ./scripts/backup-env-to-s3.sh >> /var/log/klarvido-backup.log 2>&1
```

To restore after a total VPS loss, on the new VPS before starting any containers:

```bash
aws s3 cp s3://<bucket>/env-backups/<timestamp>.env.enc ./env-backup.enc
openssl enc -d -aes-256-cbc -pbkdf2 -in env-backup.enc -out .env -pass pass:'<passphrase from password manager>'
```

## Updates and Deployments

### Manual Update

```bash
cd /opt/saas-app

# Pull latest code
git pull origin main

# Rebuild and restart services
docker compose -f docker-compose.prod.yml --env-file .env.prod build
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d

# Run migrations
docker compose -f docker-compose.prod.yml exec backend python manage.py migrate
```

### Automated Updates with Watchtower

Add Watchtower to your docker-compose.prod.yml:

```yaml
services:
  watchtower:
    image: containrrr/watchtower
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock
    environment:
      - WATCHTOWER_CLEANUP=true
      - WATCHTOWER_POLL_INTERVAL=300
    restart: unless-stopped
```

### Publishing Translations

`deploy-vps.yml` already syncs translation keys and imports translated content on every
deploy (non-destructively, new/changed keys only - via `run_migrations.sh`), and the
webapp serves them live from the backend's own `/api/translations/{locale}.json` by
default, so translations work out of the box with no extra step. The separate,
manually-triggered **"Publish Translations to VPS"** GitHub Actions workflow
(`.github/workflows/publish-translations.yml`) additionally snapshots a
`TranslationVersion` and pushes a JSON bundle straight to the configured storage backend
(S3/R2/etc, see [Storage Options](#storage-options)) - only needed if you've set
`VITE_TRANSLATIONS_URL` to serve translations directly from cloud storage/CDN instead of
through the API, or want to force a fresh published snapshot without a full redeploy. Run
it from the Actions tab after merging translation content changes you want live
immediately in that mode.

## Monitoring

### Uptime Monitoring with Uptime Kuma

Add to docker-compose.prod.yml:

```yaml
services:
  uptime-kuma:
    image: louislam/uptime-kuma:1
    volumes:
      - uptime_data:/app/data
    networks:
      - web
    labels:
      - "traefik.enable=true"
      - "traefik.http.routers.uptime.rule=Host(`status.${DOMAIN}`)"
      - "traefik.http.routers.uptime.tls.certresolver=letsencrypt"
```

### View Logs

```bash
# All services
docker compose -f docker-compose.prod.yml logs -f

# Specific service
docker compose -f docker-compose.prod.yml logs -f backend

# Last 100 lines
docker compose -f docker-compose.prod.yml logs --tail=100 backend
```

### Resource Monitoring

```bash
# Container stats
docker stats

# System resources
htop
df -h
```

## Security

### Firewall Configuration

```bash
# Install UFW
sudo apt install ufw

# Allow SSH, HTTP, HTTPS
sudo ufw allow 22/tcp
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp

# Enable firewall
sudo ufw enable
```

### Fail2ban

```bash
# Install
sudo apt install fail2ban

# Configure for SSH
sudo cp /etc/fail2ban/jail.conf /etc/fail2ban/jail.local
sudo systemctl enable fail2ban
sudo systemctl start fail2ban
```

### Automatic Security Updates

```bash
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades
```

## Troubleshooting

### Container Won't Start

```bash
# Check logs
docker compose -f docker-compose.prod.yml logs backend

# Check container status
docker compose -f docker-compose.prod.yml ps

# Inspect container
docker inspect saas-backend
```

### Database Connection Issues

```bash
# Check database is running
docker compose -f docker-compose.prod.yml exec db pg_isready

# Connect to database
docker compose -f docker-compose.prod.yml exec db psql -U backend
```

### SSL Certificate Issues

```bash
# Check Traefik logs
docker compose -f docker-compose.prod.yml logs traefik

# Verify DNS
dig +short api.yourdomain.com
```

## Scaling

### Scale Celery Workers

```bash
docker compose -f docker-compose.prod.yml up -d --scale celery_worker=3
```

### Vertical Scaling

Upgrade your VPS to a larger plan, then restart containers:

```bash
docker compose -f docker-compose.prod.yml restart
```
