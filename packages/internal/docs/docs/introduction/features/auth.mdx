SaaS Boilerplate comes packed with authentication and authorization functionality that is built-in, making it easy for
you to secure your SaaS application. The system includes login, signup, and password forgot pages, as well as email
verification, to ensure that only authorized users can access your application.

### Login and Sign up

The login and signup pages are designed to be simple and user-friendly (and fully customisable). Users can log in with
their email address and password, or they can use social authentication with Google or Facebook. The signup page
allows new users to register for an account by providing their email address and password.

Social sign-in identifies an account through its existing Google or Facebook association. A matching email address
does not automatically link a social identity to a password account or another provider's account, and the
provider must itself report that email as verified (Google's `email_verified` claim) - an unverified provider
email is rejected outright, whether it would have created a new account or matched an existing one.

For a verified existing account, the first provider connection redirects to the login page and requires the
account password plus OTP if enabled, or a verified passkey. Confirmation expires after five minutes and can
be cancelled. Linking sends the account owner a notification email so an unexpected connection is noticed.
After linking, social sign-in requires OTP when enabled; direct verified passkey login remains an alternative
without an additional OTP step.

A matching but unconfirmed account is never automatically reclaimed by a social login - the real owner may
simply not have confirmed yet, and could already hold organization data. Instead the login page explains that
an account with that email exists, points the owner at the normal sign-in-and-verify path, and directs anyone
who didn't create the account to contact support. Support can resolve a genuine dispute from Django Admin's
Users list ("Reclaim unconfirmed account" action, superusers only) after verifying ownership out of band: it
strips the account's password, OTP, passkeys, sessions and any social links, then emails a password-reset link
to let the rightful owner back in.

Connected social providers can be disconnected from Profile → Connected social accounts. Removal requires
fresh password authentication plus OTP if enabled, or a verified passkey. The last login method cannot be
removed. Disconnecting cancels pending links and revokes all sessions, including the current session.

Support reclaim also invalidates existing confirmation-email links, password-reset links and pending OTP
login proofs, and removes pending passkey challenges and management grants. Older confirmation-email links
issued before this token hardening need to be resent. Both confirmation and password-reset completion recheck
their token under an account lock, so an in-flight request cannot restore credentials after reclaim.

The translation data migration fills these security messages and replaces English placeholders while
preserving customized translations. Publish all locales from Django Admin after deployment to update the
runtime translation files; bundled fallbacks and the deployment translation export also contain the messages.

For historical accounts, run `python manage.py review_social_links --details` in the backend to obtain a
read-only inventory of social links without recorded fresh ownership proof. The report omits email addresses
and provider UIDs. Missing proof does not establish abuse: legacy records do not capture linking provenance.
Verify mailbox ownership, review registered credentials and organization memberships, and check the security
history before recovery. New verified provider signups and explicit links record their ownership proof. Confirmed accounts require an incident review; the unconfirmed reclaim action must
not be used for them. This command never removes links, credentials or memberships automatically.

### Signup and email verification

Successful email/password signup immediately logs the new user in and opens the main panel, even before
email verification. An activation email is queued for delivery. Existing accounts are never overwritten or
logged in through signup; duplicate-email validation remains. This product behavior leaves signup account
enumeration (E13) as an accepted product risk with no action needed. Connecting Google and other operations requiring verified ownership still enforce it.

Google sign-in starts through a CSRF-protected browser POST. Deployments must apply the upgraded
social-auth package migrations along with application migrations and rebuild the backend and workers.

### Authentication audit and security emails

Password and OTP authentication outcomes and credential changes have durable security records.
Account audit records and notification delivery status are available to superusers in Django Admin;
these account records are independent of an organization’s activity-log toggle.

Password changes/reset completions and authenticator enablement, replacement and removal notify the
account owner. The database outbox survives broker outages and is swept every 30 seconds by Celery Beat.
Run the regular Celery worker and Beat services on every deployment target. Failed deliveries retry up to
eight times; exhausted retries remain visible in administration. Delivery can repeat after a crash between
SMTP acceptance and recording success. A notification-delivery failure does not undo a committed change.

The new account audit family and notification recipient data use 90-day retention by default, configurable
through `AUTH_AUDIT_RETENTION_DAYS`. Cleanup processes bounded batches daily. Set
`AUTH_AUDIT_TRUSTED_PROXIES` to trusted, sanitizing reverse-proxy CIDRs to record forwarded client IPs;
otherwise the direct peer address is recorded. Audit records exclude credential material and raw request data.
Rebuild the email renderer when deploying the new notification templates.

### Recovery limits and password validation

Password-reset requests always show the generic confirmation. The configured reset policy defaults to
five requests per IP/hour, one email/address every five minutes, five/address per UTC day and 500 newly
queued messages/hour globally. Suppressed requests do not disclose account existence; unavailable limit
checks suppress delivery. `AUTH_AUDIT_TRUSTED_PROXIES` also controls forwarded IP handling for reset limits.
Reset links expire after one hour, including previously issued links. Email-confirmation expiry is unchanged.

New passwords retain the eight-character minimum by product decision. Server checks compare them with
account email/profile names and a local common-password corpus plus application-specific predictable
choices. Existing passwords still work. No external password-check service or forced password resets are used.

### OTP encryption deployment requirement

**Before merging this branch to master or deploying to the VPS, add `OTP_ENCRYPTION_KEYS` to the private
VPS environment.** Generate a dedicated key with:

```sh
python -c 'import base64,secrets; print(base64.b64encode(secrets.token_bytes(32)).decode())'
```

Keep the key out of Git and database backups; maintain a separate recoverable key backup. API, migrations,
workers and Beat must share the same keyring. A mounted key file can be configured through
`OTP_ENCRYPTION_KEYS_FILE` on deployments that support it. AWS deployments provision the variable through
the existing backend secret mechanism; Render services configure it on every backend process.

VPS CI/CLI deploys stop old backend/worker/Beat writers before migration; missing key configuration blocks Compose before deployment. On other targets, stop authentication writers during migration. The migration encrypts active/pending OTP seeds before
removing plaintext columns; existing authenticators and pending login proofs remain usable. This migration
cannot be reversed to plaintext. A rollback requires coordinated old-code/database restoration. Old plaintext
backups and historical PostgreSQL pages/WAL can still contain secrets and need restricted retention; conversion does not securely erase historical storage.

For rotation, deploy `new-key,old-key` to all processes and run `python manage.py rotate_otp_keys`. After
successful conversion, remove the old key from live configuration while retaining it offline for backup recovery.
OTP secrets are never exported through user metadata/admin forms; authorized enrollment still returns the
seed/provisioning URL required to display the QR code.

### Monitoring privacy

Authentication bodies, headers, OTP material and credential-bearing URL values are filtered before Sentry
or X-Ray export and in application/server logging. Default monitoring PII capture is disabled. Frontend pages
use `strict-origin`; reset-link URLs remain usable after refresh. Review historical monitoring records and any
external proxy/CDN logs separately because application filters do not delete previously collected data.

### Profile Page

Once a user has logged in, they can access their profile page. From here, they can:

- Edit their first and last name
- Update their avatar
- Change their password
- Enable two-factor authentication (2FA)
- Manage passkeys for passwordless login
- View and manage active sessions across devices

2FA adds an additional layer of security to the application, making it more difficult for unauthorized users to access
user accounts.

:::info
Enabling 2FA for the first time only needs the current session - an account with no password and no passkey
yet (e.g. a Google-only sign-in) would otherwise have no way to ever turn 2FA on. Any later change -
replacing the secret or disabling 2FA - always requires fresh proof: your password plus your current code, a
verified passkey, or, only for an account with neither, that current code by itself. Every enable, replace or
disable sends a notification email, so an unexpected one is a signal to review your account.
:::

### Active Sessions

Users can view and manage their active sign-in sessions from the Profile page. This allows users to:

- See all devices where they are currently signed in
- Identify their current session
- Sign out from other devices remotely
- Sign out from all other sessions at once

:::info
Session management is a personal feature. Each user manages their own sessions - organization admins cannot view or manage other users' sessions for privacy reasons.
:::

### Role Management

User rights are implemented with the role management system. This system allows you to define roles and assign them to
users. The roles determine what actions a user can perform within the application. For example, you can create an admin
role that has access to all features of the application, while a standard user role only has access to basic features.

### Enterprise SSO & Passkeys

For enterprise customers, SaaS Boilerplate includes advanced authentication options:

- **SAML 2.0 & OIDC SSO** - Allow enterprise customers to use their identity providers (Okta, Azure AD, etc.)
- **WebAuthn/Passkeys** - Passwordless authentication using biometrics and security keys
- **SCIM 2.0** - Automated user provisioning and directory sync
- **Domain-based SSO Discovery** - Automatically detect when a user's email domain has SSO configured
- **Per-tenant SSO Configuration** - Each organization can configure their own SSO settings

:::info Where is each feature managed?

- **SSO/SCIM/Audit Logs** - Organization-level, managed by tenant admins in **Organization Settings → Security**
- **Passkeys** - Personal credentials, managed by each user in their **Profile → Passkeys**
- **Active Sessions** - Personal, managed by each user in their **Profile → Active Sessions**
  :::

These features are enabled by default and can be configured via environment variables:

```bash
VITE_ENABLE_PASSKEYS=true     # Enable passkey/WebAuthn login
```

See the [Enterprise SSO Guide](/features/enterprise-sso) for complete setup instructions.
